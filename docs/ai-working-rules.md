# AI作業の効率と成果に関するルール

ClimbLog専用。AGENTS.md・開発運用ルール・公開方針と併用する。効率は「少ない消費で、検証済みの必要な成果を得ること」とする。クレジット消費や作業時間を埋めることを目的にしない。安全・互換性・ユーザーの指示を省略して節約しない。

## 1. 最初に範囲を決める
- 対象リポジトリ・ブランチ・未コミット変更を一度確認し、依頼の完了条件、対象外、必要な検証を短く整理する。既存のルール・実装・テストから分かることを先に調べる。
- 作業は効果・利用頻度・困りやすさ・リスクで選ぶ。効果が明確な最小変更から進め、無関係な整理、機能追加、全面書き直しを混ぜない。
- 不明点は、安全に進められる部分を先に実施し、結果に影響する質問だけまとめる。承認済みの通常作業を繰り返し確認しない。必要な承認は省略しない。

## 2. 読む量と呼び出しを抑える
- 検索は対象フォルダを限定したrg/rg --filesから始める。親フォルダ、他アプリ、機密ファイルを探索しない。
- 関連箇所と呼び出し元・保存形式・既存テストを読む。巨大なファイルや圧縮された長い行は必要な関数・範囲を切り出し、毎回全体を出力しない。
- 独立した読み取りと検索はまとめる。変更や前提に依存する操作は順番に行う。依存関係を無視した並列実行で失敗を増やさない。
- 同じ会話で読んだルールや確認済みの結果は再利用する。新しい変更、状態変化、古くなった可能性がある場合だけ再確認する。
- 出力は必要な差分・件数・失敗箇所を中心にする。長いログや同じ内容を会話・文書・エージェント報告へ重複して貼らない。ログや画面例は公開ソースに含めない。

## 3. エージェントを増やしすぎない
- 基本は主担当1名。分担が許可され、独立した調査・危険箇所のレビューに効果がある場合だけサポート1名を使う。単純な文言・配置・文書の修正で増員しない。
- 分担時は目的、対象ファイル、禁止事項、必要な結果を限定する。同じ調査を二重に依頼せず、同じファイルを同時編集しない。
- 代表者が重複・矛盾を解消する。補助担当が制限や障害で動かなければ、別の担当を次々起動せず、必要な仕事を主担当へ戻す。
- モデルを選べる環境でも、実際の選択権限と作業の難しさに応じて判断する。課金プランやモデル設定を無断で変更せず、消費削減量を推測で保証しない。

## 4. 小さく実装して原因を確かめる
- 既存の部品・データ定義・保存経路・検証を再利用する。必要性のない依存、抽象化、独自の重複定義を追加しない。
- 失敗したらまずエラーと前提を確認し、原因の仮説を立てて1つずつ確かめる。同じ操作を根拠なく繰り返さず、試行前に何を確認するかを決める。
- 予想より範囲が広がった場合は、検証済みの変更と未完了を区別して優先順位を見直す。機能廃止・データ削除・互換性破壊・課金・新しい個人情報送信は既存の承認ルールに従う。

## 5. 変更に合う検証だけを確実に行う
|変更|主な確認|
|文書のみ|差分・参照先・内容の整合性。実行コードが変わらなければブラウザーや実API試験はしない|
|画面・入力|関連する操作、スマホ/PC、両テーマ、入力保持、キーボード、横はみ出し|
|データ・計算|意味のある境界値、旧形式、編集・保存・復元、実績と予定の区別|
|認証・同期|アカウント分離、認証切れ、通信失敗、競合、未送信データ|
|配信・キャッシュ|公開処理と配信対象。画面資源が変わる場合はService Worker更新と関連PWA試験|
- テストはモックとサンプルを基本にし、本番データを変更しない。既存の適切なテストを先に使い、新しい不具合・非自明な分岐を確認する場合に必要な回帰テストを追加する。
- 成功した検証は結果を再利用する。追加変更・失敗・未解決の懸念がない限り、同じ全テストを繰り返さない。実装や期待値を都合よく変更して失敗を隠さない。
- 関連チェックが終わる前に公開しない。モック、画面幅、iPhone実機、実APIを区別して報告する。公開後はCIと必要な配信資源を一度確認し、目的のない再確認をしない。

## 6. 開発クレジットとアプリのAPI枠を分ける
- AI開発ツールのクレジットとGeminiなどのAPI利用枠は別管理。残量・回復時刻・料金を確認できない場合は断定せず、長時間稼働や一定額以内を保証しない。
- 実APIは本人の許可、対象、送信範囲、試行上限がある場合だけ呼ぶ。先にモックで設定・応答・異常系を検証する。自動再試行、無断の上限リセット、有料モデルへの自動切替はしない。
- コースの再利用・サーバー側回数制限・利用間隔・秘密管理を維持する。状態確認や画面確認のつもりで生成処理を呼ばない。

## 7. 時間と報告
- 期限がある場合は開始時と実装から検証へ移る時点で時刻を確認し、最後の約2割を収束・テスト・公開確認・報告に確保する。開始時に期限が過ぎていれば確認する。
- 新しい作業を期限ぎりぎりまで増やさない。間に合わない変更は未検証のまま本番へ混ぜず、作業ブランチに残して状態を報告する。
- 改善効果がなくなったら終了する。必要な作業が完了した後に消費を増やすためだけの調査・検証・提案を続けない。
- 進捗は新しい発見・判断・次に解消する不確実性を短く伝える。最終報告は変更、検証、公開状況、未確認事項を中心にし、作業ログを列挙しない。
