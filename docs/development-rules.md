# ClimbLog の開発・運用ルール

## アプリの境界
この文書とルートの `AGENTS.md` はClimbLog専用。親や兄弟アプリにルールファイルを勝手に作成しない。他アプリの変更が必要な依頼は、その対象と公開先を別途特定する。ローカル作業ルートは `C:/Users/sskwo/source/repos/climblog`、正しいoriginは `https://github.com/HAYATE-ama/climblog.git`。移動時はGit履歴・非公開ファイルを含めて確認し、参照先と所有権を検証する。

## 変更の進め方
1. 作業ルート、現在ブランチ、未コミット変更、originを確認する。
2. 依頼の範囲を把握し、関係するモジュールと既存仕様を読む。既存のユーザー変更を混ぜない。
3. 目的が分かる作業ブランチで最小限の修正を行う。関連しない整理や一括フォーマットは避ける。
4. 関連テスト、差分、公開対象を確認する。必要な資源だけ明示的にステージする。
5. 承認済みの公開方針に沿いpush・main統合・Actions成功・配信反映を確認する。
6. 変更内容・確認した環境・未確認事項を報告する。

## ファイルの責務
- `index.html`：画面の土台。`assets/js/`：UIとモデル、認証・同期。`assets/css/`：画面別スタイル。
- `supabase/`：DB定義・RLS。`tests/`：サンプルを使った単体・画面検証。`docs/`：仕様・操作・運用。
- `.github/workflows/pages.yml`：テストと配信。配信対象はindex/config/manifest/Service Worker/assetsだけ。
- `production/` は開発対象を切り替える理由にしない。実際の配信元はリポジトリ直下の現行資源。
- `config.example.js` は秘密を含まない例。`config.js` に置けるのは公開URLと公開キー。
- `private/`・`local-only/`・`backups/` とローカルアカウントメモはGit管理対象外。実データは公開しない。

## 複数アプリを並行開発する場合
- アプリごとにリポジトリ・VS Codeのフォルダ・ブランチ・設定・依存管理を分ける。兄弟フォルダを一括編集しない。
- ローカルサーバーは別ポートを使用し、既存プロセスを止める前に自分が起動したものか確認する。テストは空いている自動割り当てポートを優先する。
- Supabaseのプロジェクト、Authの許可URL、DB、Storage、クラウド環境変数はアプリ別に明確化する。別アプリのキーやデータを流用しない。
- テストと本番は、接続先または専用アカウントで区別する。実ユーザーのデータをサンプルとして使わない。
- 同一originの場合はlocalStorageとService Workerが衝突し得る。ストレージキー、キャッシュ名、scope、公開サブパスをアプリ固有にする。
- GitHub Actions、公開URL、認証設定、ドメインを変更する際はアプリ名とリポジトリを照合する。

## 互換性と品質
日本語で簡潔なUIを保ち、HTMLへ挿入するユーザー入力はエスケープする。入力検証は保存・復元・同期でも行う。ボタンの見た目だけで権限を制限せず、認証とRLSで保護する。依存追加時は必要性・ライセンス・更新コストを確認し、秘密を外部へ送るライブラリを無断で追加しない。
保存済みの記録・メニューID・左右・実績と予定・測定条件は意味を保つ。DB変更は非破壊の追加を優先し、既存データの読み込みと移行・バックアップ・復元を確認する。公開履歴はrevertで戻すことを基本とし、DBや実記録を巻き戻しのために削除しない。

## 必要な確認
モデル変更は単体テスト、画面変更は操作と表示、同期変更は認証・アカウント分離・競合・未送信データ、配信変更はPWAとキャッシュを確認する。関連チェックが成功したら、根拠なく全テストを何度も繰り返さない。ブラウザー幅の確認とiPhone実機確認を区別する。自動検査だけで秘密や個人情報を完全検出できたとは主張しない。

## 各アプリで独立して用意する文書
別アプリを作成するときの確認リスト。ここにClimbLogの値を流用せず、そのアプリ内に個別に作成する。
- AGENTS.md：アプリ名・作業範囲・対象外・禁止操作・検証方法。
- README.md：目的・動かし方・構成・設定方法。
- 設定例と.gitignore：公開値/秘密の区別、ローカル専用情報の置き場所。
- 環境一覧：ローカル/テスト/本番のDB、公開先、アカウント分離。秘密の実値は書かない。
- データ仕様：保存形式・単位・ID・互換性・移行/バックアップ方針。
- UI方針：対応端末・テーマ・アクセシビリティ・主要な画面遷移。
- テスト手順：サンプルデータ・実行コマンド・未対応環境。
- リリース方針：ブランチ・公開対象・CI・確認・取り消し手順。
- 外部連携方針：認証・権限・送信データ・費用・利用ライセンス。
既存文書で満たせる項目は重複して増やさず、リンクで参照する。
