# ログインの待ち時間改善

初回のパスワードログインでは、成功後のlocation.reloadを省き、そのページでサーバー本人確認とアカウントデータ取得を開始する。検証getUserとRLS付きuser_app_stateの読み取りを並列化する。両方が成功しユーザーIDが一致するまで、既存のキャッシュを書き換えず、アプリを表示しない。DBを先読みしても保存・更新は行わず、従来通りRLSで本人のデータに限定する。未同期・競合の選択、読み込み失敗時に端末データを残す挙動、セッションの期限は変更しない。

ログインフォームにフォーカスした時点とセッション復元開始時点で、静的な画面モジュール2つをmodulepreloadする。実行・個人データの読み込みは認証完了後。認証コードが準備されるまで送信ボタンを無効にして、ロード中の早すぎる送信によるページ再読み込みを防ぐ。

既に画面モジュールを実行した後の再認証・アカウント変更では、モジュールに残る状態を混ぜないよう従来のページ再読み込みを維持する。保存済みセッションからの起動もサーバー本人確認を維持する。APIキーや秘密ファイルは不要で、参照しない。

検証：tests/auth-startup.test.mjs（並列性・両方の完了・不一致・失敗・空のアカウント）、tests/browser/auth-performance.mjs（初回再読み込みなし・表示前の検証・遅延条件での比較）、既存auth-session.mjs（期限・未同期・競合・複数タブ・アカウント分離・途中記録）。テストの認証・DBは隔離したモックで、本番アカウントは使用しない。

固定の待ち時間（本人確認180ms・データ取得220ms）を入れた修正前比較では、スマホ幅685ms、PC679ms、成功後に1回のページ再読み込み、本人確認とデータ取得の開始差183/186ms。修正後はスマホ幅439〜457ms、PC406〜418ms、成功後の再読み込み0回、本人確認と記録取得の開始差0ms。数値はテスト条件での測定で、実回線・Supabaseの起動時間・SDK配信時間を保証するものではない。実機iPhone未確認。

根拠：https://supabase.com/docs/reference/javascript/auth-getuser 、https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/modulepreload
